# RUNE_MIGRATION.md — from GPUI to Rune

The record of the 2026-11-08 UI-framework migration:
why it happened, what was removed, what replaced it,
what it cost, and how the framework pin is maintained.
Status at the time of writing: Phases A–C delivered and
CI-green; Phase D (feature rebuild) in progress.

## 1. The decision

The editor's shell was built on GPUI 0.2.2 through
fifteen waves (peak state: CI run 42451617130 green,
912 tests). The owner's real-desktop screenshot of the
Wave 15 shell settled the argument against continuing
with it: the stage canvas was squeezed to a ~90 px strip
by the tool band, menus rendered as a full-width row
that pushed the layout down, frame chips were duplicated
across rows, and — structurally worst — **nothing visual
could be verified anywhere but a human's screen**: the
dev VM renders the GUI black, so every redesign wave
shipped CI-green but screenshot-blind.

The owner directed a full framework replacement:
remove GPUI entirely and rebuild on
[Rune](https://github.com/anomalyco/rune) (anomalyco),
a native GPU-rendered Rust UI framework whose binaries
can render themselves headlessly to PNG and dump their
element tree — the verification capability GPUI never
gave this project.

## 2. Phase A — audit before code (delivered)

`docs/RUNE_API_AUDIT.md` was written from the framework
**source** at the pinned revision before anything was
deleted. Headline findings:

- App entry is one call, `rune::run(AppSpec::new(..))`,
  with title, size and `min_size` on the spec.
- The stage is a `canvas(Shape)` element: polylines with
  width and caps, polygon fills, Bézier paths, one
  instanced draw call per frame; shapes can change every
  frame. A stick figure is one canvas element built from
  the solved rig.
- Pointer input is complete: `on_drag` with element-local
  points and built-in capture, `on_secondary_press`,
  wheel/magnify for the camera. Playback maps to
  `AppSpec::poll` + `tx.wake_after(..)`.
- Text input is real at two layers (core `TextEdit` with
  IME preedit; kit `TextField`/`TextInput`/`TextArea`).
  Menus, popovers, dialogs and tooltips exist in core
  and kit — as floating anchored layers, so the Wave 15
  menu-row defect cannot recur by construction.
- Our own rasterizer's RGBA output feeds image elements
  directly (`ImageCache::rgba`), so export previews and
  project thumbnails need no new decode stack.
- Headless: every Rune binary parses `--snap out.png`,
  `--tree out.json`, `--scene`, `--script`, `--at`,
  `--crop`; headless rendering runs a deterministic
  virtual-clock loop through the real GPU renderer.
  An in-process `Runtime` API (`find` / `presented` /
  pointer / key) drives interaction tests in
  `cargo test` with no GPU at all.
- rune-i18n was evaluated and deliberately **not**
  adopted: our 28-language flat table already works; it
  buys plurals we do not need at the cost of a build.rs.

Verified gaps (small, and worked around, not hidden):
no circle/arc primitive in `Shape` (joints and heads
are polygons), no text inside a canvas `Shape` (labels
are elements), no slider in rune-kit (hand-rolled once
from the settings example's proven `on_drag` pattern),
and translucent strokes double-blend where they overlap
at a joint (onion-skin alphas were chosen with this in
mind).

Left marked UNPROVEN by the audit: pixel snapping on a
GPU-less CI runner (needs a software Vulkan adapter),
Linux IME behaviour, and touch input.

## 3. Phase B — GPUI removed (delivered)

Commit `6f03dd4`. Deleted:

- `src/app.rs` — the 5,499-line GPUI `EditorView`
  monolith;
- `src/app/` — the stopped partial module split;
- `src/ui/` — the entire GPUI component library;
- the `gpui = "=0.2.2"` dependency, its
  `[patch.crates-io]` section, and the vendored
  `vendor/xattr` copy that existed only for GPUI;
- the `app` / `ui` module declarations and aliases in
  `src/lib.rs` — the library is now engine-only
  (28 modules).

`Cargo.lock` was regenerated by the resolver: 433
packages, zero GPUI. CI run **42455193634** green:
**701 tests passed (691 unit + 10 integration)**.

The honest arithmetic: the suite went from 912 (GPUI
peak) to 701. Nothing was lost silently — ~211 of the
old tests lived inside the deleted GPUI UI files and
tested presentation code that no longer exists. Every
engine, format, export and determinism test is intact,
and the MCP server (65 tools) never imported GPUI in
the first place.

## 4. Phase C — the Rune editor shell (delivered)

Commit `7083701`. Three files, 728 lines, declared as
modules of the binary only (`src/lib.rs` untouched):

- `src/main.rs` (212) — `AppSpec` entry (1440×900
  window, 1280×720 min), state = `EditorCore`, poll
  clock, keyboard routing;
- `src/stage_view.rs` (324) — the stage canvas;
- `src/chrome_view.rs` (192) — app bar, timeline,
  transport, status line.

What it does — all wired to real engine ops, no
placeholder controls:

- Stage draws **all figures** at the displayed frame
  via `positions_f` (graph-channel aware): per-node
  colours at real thickness, shape nodes, head rings,
  and onion skins (previous frames in figure colour at
  the GPUI shell's exact alpha falloff, next frames in
  green).
- Drag posing through `begin_drag` / `drag_to` /
  `end_drag` (hit-testing, FK aim, two-bone IK, root
  move), plus the core's camera-drag and draw-drag
  modes. Drawing and dragging share one
  `view_transform`; its `to_stage ∘ to_screen`
  roundtrip is unit-tested exact, so the figure tracks
  the cursor with no offset.
- Wheel zoom (coalesced per 1.1× step, because the
  core's zoom op snapshots per call), app-bar Save /
  Load / Undo / Redo / + Figure / Onion, clickable
  numbered frame chips with Add / Duplicate / Delete
  frame, transport (prev / play-pause / next) playing
  through `advance_play` — fps, per-frame durations
  and loop range honoured — and keyboard: space,
  arrows, Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y, Delete
  (segment).

CI run **42456311759** green: **708 tests passed
(691 unit + 7 new binary tests + 10 integration)**.

## 5. Phase D — feature rebuild (in progress)

The GPUI-era surface returns section by section as
binary modules under `src/rune_sec/`, each wired to
the same engine ops the GPUI panels called: figures
panel; segment and style inspectors; camera panel;
scene panel; frames and keyframes; graph panel;
easing panel; draw mode and strokes; FX panel; audio
panel; movieclips; figure library; 3D session; export
centre; Home; floating menus; command palette;
settings; help; toasts; status; onion and playback
controls; pose tools; layers; text segments; projects;
stats. Two verification sections ride along:
in-process `Runtime` interaction tests (the old
248-command preservation inventory becomes executable)
and named `AppSpec` scenes so `--snap` / `--tree` can
check each workspace headlessly.

At the time of writing, the first section files
(figures panel, camera panel, scene panel, easing
panel, segment inspector, style inspector, figure add)
are in the tree but **not yet wired into `main.rs`**,
and Phase D makes no CI-green claim until its
integration run passes.

## 6. The pin

Rune has **no releases** — no crates.io presence, no
tags; consumers pin a `dev` revision. Ours, in
`Cargo.toml`:

```toml
rune     = { git = "https://github.com/anomalyco/rune", rev = "87caf2a3a2d9e3fb6172f5a62997748dbf25748e" }
rune-kit = { git = "https://github.com/anomalyco/rune", rev = "87caf2a3a2d9e3fb6172f5a62997748dbf25748e" }
```

Both crates pin the **same** revision (rune-kit depends
on rune internally). The audited source this record is
based on is kept locally at `~/workspace/rune-src`
(rev 87caf2a). Rune's own stack: wgpu ~30, winit
0.30.13, taffy 0.15, parley/swash/fontique text;
edition 2024 under toolchain 1.99.1 — the same rustc
this project already used.

## 7. Risks (standing)

- **API churn.** Upstream lands multiple commits a
  day; types apps build as literals (including
  `AppSpec` and `ScrollSpec`) can gain breaking fields.
  The pin is the mitigation; a floating branch is
  never acceptable.
- **macOS-first centre of gravity.** The default Apple
  path is a custom Metal backend; several behaviours
  are macOS-led. Linux is a real target (winit
  x11/wayland, wgpu Vulkan) but rough edges will be
  found by us, not by their screenshots. Linux text
  smoothing defaults to Off (antialiased, browser-like).
- **IME on Linux** is the framework authors' own
  named top risk (their PLAN.md §9.1). It is
  implemented from the native protocols; it must be
  exercised in a real field before the command palette
  is designed around it.
- **Headless pixels need a GPU adapter object.** On
  the GPU-less CI runner that means software Vulkan
  (lavapipe) — UNPROVEN at the time of writing. The
  fallback (`--tree` + `Runtime` tests in CI, snaps on
  a real machine) still exceeds everything the GPUI
  shell could verify.
- **Touch** under Rune is unaudited (a `TouchPhase`
  type exists). Nothing was lost — GPUI had none at
  all — but nothing is claimed either.

## 8. Upgrading the pin (procedure)

Per the repo's `AGENTS.md`, CI is the only build
environment; a pin upgrade is a commit + CI loop like
any other change.

1. Read Rune's `CHANGELOG.md` between the current rev
   and the target rev — it specifically lists changes
   that can move an app's output without a code change.
2. Bump `rev` on **both** `Cargo.toml` lines to the
   same new full hash. Never a branch name.
3. Push; read the Build, Test & Binary run. Expect
   literal-built types (`AppSpec`, `ScrollSpec`, kit
   specs) to be the first breakage surface; fix from
   the CI logs.
4. With CI green, run the headless checks: `--tree`
   dumps for each named scene, `Runtime` tests in the
   suite, and `--snap` PNGs wherever an adapter exists.
5. Record the new rev, the CI run id and any API fixes
   in this file (§3–§5 style) in the same commit.

## 9. What did not change

The migration was a shell replacement, not a rewrite.
Unchanged and still CI-verified: the document model
and FK/IK posing engine, the graph engine, drawing
and audio engines, VFX and weather, the 3D session,
all format codecs (.piv v2–v5, .stk, .nodes,
.nodemc/.stknds), every exporter and the
byte-determinism suite, the MCP server and its
65 tools, projects/recovery shell services, and the
28-language string table.
